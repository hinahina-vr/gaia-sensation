## 切り出し前に対応する点

### 追加方針：本番未使用データは提出側に含めない

ユーザー指示：「本番に使ってないデータは削除する感じで」。削除対象は新しい提出・本番リポジトリへの切り出し内容であり、開発側の元データや既存証跡は保持する。

- data配下は自動的な採用候補から外し、参照確認後の明示採用にする。単なる文字列検索で見つからないことだけでは未使用と断定しない。
- 初期表示だけでなく、全展示・全地域・年次切替・遅延読込・動的URL・圧縮JSON・通信失敗時の保存値まで使用範囲を確認する。
- 生データ、取得キャッシュ、中間生成物、旧版・試作・重複データは、本番実行・必要なビルド／検査に不要なら除外する。生成手順と出典リンクは残し、開発用の再取得・生成処理だけのために巨大な元データを提出側へ同梱しない。
- ライセンス・帰属・権利確認用の記録は「画面がfetchしない」だけで削除しない。除外により生成・検査コマンドが壊れる場合は、開発専用と提出用の責務を整理し、必要な検査を維持する。
- 除外理由・参照元・前後のサイズを一覧化し、新規展開した提出候補で404、表示、保存値への切替、必要なビルドを確認するまで削除済み／検証済みとはしない。

準備ツールは分類案だけを更新する。今回データの実削除や切り出しは行っていない。上記「準備済み」の5911ファイルの内訳は初回棚卸しの履歴であり、この追加方針による再実行結果は別のartifactsディレクトリへ保存する。

| 項目 | 状況・対応 |
|---|---|
| 並行開発 | 既存の変更・未追跡ファイルをそのまま保持。提出時点の完成版を確定・コミットしてからそのSHAを固定。開発はその後も続行できる |
| 素材の由来 | `build-media-rights-ledger.mjs` は `git log --reverse --diff-filter=A` で初出日を算出する。履歴を切ると変わるため、元の由来情報をハッシュとともに保全し、検証可能な移行記録として引き継ぐ方式が必要。今回直した開発側の権利記録は変更しない |
| 内部メモ | `docs/internal` やQA記録を一括削除しない。権利記録のdecisionEvidence/sourceLedger、台本生成、テストが参照する記録を洗い出し、必要な根拠だけを公開向けの来歴資料に整理する。私的判断記録は開発側に残す。根拠の捏造や検査の無効化で通さない |
| 画像・冊子 | `artifacts/gx-setting-bible/*.png` は作品素材。`output` にも設定資料PDFがある。実行時・公開文書の参照を確認し、必要なら提出側のassetsへ移設して参照を直す。フォルダ丸ごと除外しない |
| ソース・テスト | package.jsonの実行スクリプト、台本の生成元、センサーの移行SQL・SDK・スターターを保持。除外でnpmコマンドを壊さない。配信用ビルドだけを提出ソースとしない |
| 秘密情報 | .env、.dev.vars、鍵・キャッシュ・実DB・ログ等は含めない。Git追跡の有無だけに頼らず内容をスキャンし、漏洩した値をレポートへ転載しない。設定例は残す |
| 提出先リンク | README・審査ガイド等に旧GitHub URLがある。新リポジトリ名確定後に提出側で置換し、内部メモへのリンクが復活しないことを検査 |
| 現行CI | `.github/workflows/contest-checks.yml` は検査用で、デプロイstepはない。check:contestの読込上限は現状失敗する。ユーザーは性能項目を許容しているが、CIが自動で緑になるわけではない。公開候補では既知の例外として明示し、他の検査を省略しない |
| 進行中UI | AI・統計UI等の未完了／未検証変更は、準備ツールの合格をもって合格扱いしない |

## 本番接続方針

ローカル `wrangler.jsonc` は Pages `gaia-senseware`、公開originは `https://gaia-senseware.pages.dev`、DBバインディングは `gaia-senseware-sensors`。これはローカル設定の確認であり、管理画面上の現在のGit接続・自動デプロイ状態・権限は未確認。

新しい提出用リポジトリだけをリリース元にする。既存Pagesプロジェクトと本番DBを維持する方針を優先し、URL維持のためにプロジェクトの削除・作り直しは行わない。開発用には本番への自動配信経路を残さない。現在の接続を確認してから切り替えるまで、分離が完了したとは扱わない。

Git接続済みPagesでも自動デプロイを停止してWranglerから既存プロジェクトへ配信できる。新提出リポジトリの検証済みコミットから、手動リリースまたは明示実行のCIで配信する案を使える。Git接続先を単純に交換できると決めつけない。根拠：[Cloudflare Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/)。Git接続の設定変更は公開直前に実施する。

本番DBの初期化・削除・無断migrationは禁止。開発・試験のAPI書き込みは分離したテスト用DBで行う。新リポジトリに本番トークンをファイルとしてコピーしない。CI方式を採る場合も新リポジトリ側で最小権限のsecretを設定し、開発側のデプロイ経路を停止したことを確認する。

## 実際の切り替え順

1. 提出用の名前・所有者を決める。最初はprivateで準備し、審査員の閲覧条件を確認して公開範囲を設定する。名前案は `hinahina-vr/gaia-sensation`（未確定）。
2. 開発側の対象修正・回帰テストを完了し、正式な元コミットを固定。以後の開発変更は混ぜない。
3. 要精査ファイルと参照関係を解決し、明示したファイル一覧で履歴なしの新ディレクトリへ切り出す。元SHA・変換理由・内容ハッシュ・除外一覧を記録する。
4. 切り出し先で権利・出典・READMEリンク・秘密情報・ビルド・静的検査を実行。実ChromeでPC／スマホの入口、MAP／ラボ／AI、STORY保存読込・書出、センサー主要経路を確認。最終成果物を新規展開して再確認する。
5. 初回だけ新リポジトリの `main` に初期コミット。開発側のGit履歴は持ち込まない。以後は前回提出ファイルの一覧と照合し、追加・変更・削除を明示した通常コミットで更新する。本番側に直接変更があれば上書きせず照合する。
6. 公開指示後に提出用へpushし、同一コミットから配信。現在の本番設定・デプロイIDを記録して戻せる状態を残し、本番URLとAPIを確認する。コードのロールバックとDBの復元は別扱い。

### 履歴を切っても由来情報を保つ仕組み

- `scripts/media-origin.mjs`：元コミットSHA、元台帳SHA-256、素材パス・内容SHA-256・元の初出日を検証。素材パスの逸脱・重複・不正日付を拒否。

- 正式切り出し時にその出力を提出側の `docs/media-origin-snapshot.json` に配置する。開発側には配置していない。
- 素材台帳生成器は移行記録がある場合、内容が一致する素材だけ元の初出日を維持する。移行済み素材の内容不一致は停止する。新規パスの素材は新リポジトリでのGit記録日を使う。画像変更時は新しい開発元SHAから照合済み移行記録を作り直す。
- 元記録は履歴の代わりの署名や提供元許諾ではない。公開候補で元コミットと照合した記録をレビューし、採用・除外に応じた権利scopeの再確認も別途行う。内部の権利根拠の公開向け整理は未完了。
