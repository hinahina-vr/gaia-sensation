# パフォーマンス改善「高」の実装と再評価

対象: `2a4f51385b69a0fda1ef285b0058acae7207640b` を基点とするローカル作業ツリー。2026-09-09。既存の64展示・年度タイトル／光点演出の変更を維持。push・デプロイなし。

## 結論

前回レポートの優先度「高」2件を実装。大規模年度展示の入力応答と通常描画の負荷を改善し、31番の初期取得量を約半減した。地図上の地点・元の測定値・欠測・地点コードは減らしていない。

今回は実装直前の作業ツリーでも測り直し、その値を比較基準にした。前回レポートのスマホ63番1,704msと、今回直前の1,320msは一致しないため、前回の最も遅い値だけを使って改善率を算出していない。以下は単発の同一手順比較であり、実利用者の分布や速度保証ではない。

| 指標 | 実装直前 | 実装後 | 評価 |
| --- | ---: | ---: | --- |
| スマホ相当・63番の年度タップ | 1,320ms | 56ms | 約96%短縮 |
| スマホ相当・63番の年度キー | 1,304ms | 72ms | 約94%短縮 |
| PC・63番の年度キー | 312ms | 48ms | 約85%短縮 |
| スマホ相当・63番のメインスレッド稼働 | 82.2% | 47.2% | 約35ポイント低下 |
| スマホ相当・63番のスタイル再計算／5秒 | 1.894秒 | 0秒 | 今回の観測窓では発生せず |
| スマホ相当・63番の描画機会／秒 | 51.6 | 60.0 | 安定化 |
| 31番初期の読込済み本文量・非圧縮 | 22.638MB | 11.312MB | 約50%減 |
| 63番全国表示の地点選択肢 | 8千件超 | 案内1件 | 地域選択／地図選択後に必要な候補を作成 |

「描画機会」はrAFの頻度であり実際の表示FPSではない。年次キャンバス自体の呼出しは約20回／秒。稼働率はメインスレッドのTaskDurationであり全CPU・GPU使用率ではない。操作応答は実入力のEvent Timingであり、サイト全体のINPではない。

## 実装内容

### 高1: 地点選択欄と再レイアウト

- 全国250地点超では「先に地域を選択 / 地図から選択」を表示し、地域を選ぶとその地域の全地点を生成する。全国の光点はそのまま表示する。
- 同じ地点ID集合の年度変更ではoption要素を再利用し、値が変わったラベルだけ更新する。地図選択時の近隣・同座標の地点コード、年度をまたぐ選択ID、欠測表示も保持する。
- 地図の表示矩形を共有し、resize・scroll・画面復帰などで無効化する。カメラの移動・拡大では矩形の再読取りを繰り返さない。
- 光点の色・大きさ・地理変換の不変部分を地点単位で再利用する。
- 凡例の監視は同じ表示状態をスキップし、サイズ変化を1フレームに集約する。年次展示では不要な他パネル同期を実行しない。

対象: `src/exploration/marine-cod-exhibit.js`、`app.js`、`map-legend-drag.js`。

### 高2: 初期取得量と順序

- 共通スナップショットに `loadMode(id)` を追加。選択した展示だけ読み、分析画面が必要とする完全版は明示的に取得する。部分取得と完全取得で同じチャンク要求・JSON解析を共有する。
- 未選択のe-StatとFIRMSデータの起動時先読みを廃止。e-Statの遅い読込完了が別展示を上書きしないようガードする。
- 統計分析JSと4種類のCSSは最初の分析操作で読み込む。分析画像も遅延読込する。モバイルの操作シート経由も同じ経路。
- 年次展示への直リンクでは選択データを早めに取得。不要な共通10展示やJMA履歴、オーロラ要求を起動時に開始しない。
- データ読込中は自動デモを一時停止し、読込失敗では停止する。次展示の読込後にも25秒の表示時間を確保する。
- 年次JSONの15秒制限は維持。共通ストアの20秒制限は一式全体から各要求単位へ変更し、無関係な要求の合計時間で中断しないようにした。単に待機時間だけを引き延ばす対策ではない。
- 変更した配信JSの参照URLを `perf-high-20260909` へ更新。データファイル自体は変更していない。

対象: `src/data/snapshot-store.js`、`app.js`、`gaia-mode-loader.js`、`index.html`、`src/exploration/index.js`、`estat-exhibits.js`、`firms-exhibit.js`、`map-demo.js`、`map-demo-controller.js`。

海岸線・国境の解像度は維持した。初期取得量の残りには国境3.083MB、陸地1.636MB、沿岸COD2.627MBが含まれる。地形の解像度を下げることは今回採用していない。

## 圧縮と低速回線

既存の[公開配信の沿岸COD](https://gaia-senseware.pages.dev/data/japan-marine-cod.json?v=annual-pollution-1)を読み取り専用で確認。HTTP/2・Content-Encoding `br`、Cache-Control `public, max-age=86400, stale-while-revalidate=604800` が実際に有効だった。

2026-09-09 02:18 UTCのネットワーク取得は本文186,331B、復号後2,627,355B、147ms。続くブラウザキャッシュ利用は転送0B、4.9ms。CDNを消去した全世界のコールドキャッシュ測定ではない。今回の実装は未公開なので、この値を改修後の本番速度とは呼ばない。

`scripts/serve-novel-preview.mjs` に任意のBrotli配信を追加。通常の非圧縮動作は維持し、`GAIA_PREVIEW_COMPRESSION=br` の場合のみ有効。ローカルCODの復号後バイト列が元ファイルと完全一致することを確認（2,627,356→164,890B、Brotli品質4）。本番と圧縮方式の設定・HTTPバージョン・キャッシュは同一ではない。

下り1.6Mbps／上り0.75Mbps／遅延150ms・CPU4倍制限で、非圧縮とBrotliを別々に測定した。

| 条件 | 結果 | 注意 |
| --- | --- | --- |
| 改修後・非圧縮 | 取得開始16.20秒、15.00秒後にCOD取得中断。63.27秒時点も31番のエラー表示 | 低速・非圧縮の失敗は未解消。ただしデモは停止し、空のまま次展示へ進まない |
| 改修後・Brotli品質4 | COD取得開始6.95秒、取得2.70秒。アプリのデータ表示14.08秒、カメラ整定14.40秒 | データ表示まで完了。本文完了分1.713MBはその時点の値で、未完了の背景地形は含まない |

圧縮後も背景地形は重い。陸地は約24.28秒、国境は約30.44秒で取得完了した。44番の観測中に背景取得完了と重なる67ms・558msのLong Taskがあり、rAFは約53Hzへ一時低下した。これは「高」の対応後に残る初期化負荷で、定常時60Hzの結果と混ぜていない。国境の復号・地図更新が関係すると考えられるが、このLong Taskの内訳をプロファイルで確定したものではない。

圧縮・低速回線で63番へ初めて切り替える待ち時間は5.86秒、年度タップは72ms。圧縮版の改修前A/Bは実施していないので、非圧縮の失敗との差を全てコード改善の効果とは扱わない。

## Core Web VitalsとDevTools

Chrome DevToolsでBrotli配信の31番を再読込してトレース。ここは通信制限なしで、PC CPU1倍、スマホ相当CPU4倍。各約5秒の補助計測。

| 指標 | PC | スマホ相当 | 解釈 |
| --- | ---: | ---: | --- |
| LCP | 117ms | 250ms | 目安上は良好。ただし両方とも起動ロゴであり、地図データ準備の時刻ではない |
| CLSの最大クラスタ | 約0.0003 | 約0.0001 | 小さい |
| フィールドINP／実利用p75 | 未測定 | 未測定 | 少数のローカル入力をサイト全体のINPと呼ばない |

LCPは表示される要素と観測窓に依存する。別の自動操作測定ではPCの章タイトル要素が6.124秒でLCPになった。短い起動ロゴの値だけで地図の待ち時間を評価せず、前述のデータ準備／背景完了／入力応答を併記した。

起動時にはまだ強制レイアウトがある（PCのresize呼出し由来54ms、矩形の初回読取り21msなど）。一方、スマホ相当で63番の全8,336地点が出現した後の5.005秒トレースではForcedReflowの指摘がなく、別のCDP測定でも通常描画中のLayout／RecalcStyleは0だった。レイアウト負荷が全操作・全画面でゼロという意味ではない。

RenderBlockingの改善見積りはPC・スマホともFCP/LCP 0ms、画像改善もLCP 0ms。この条件では優先度を上げない。Lighthouseスコア・Speed Indexは未測定。

アクセシビリティツリーでは地域・測定地点・年度の名前が残り、全国地点欄が案内1件になったことを確認。最終63番の画面と、回帰テストのPC・スマホ分析画面を目視確認。スクリーンリーダー実機やコントラスト全面監査ではない。

## 証跡と再実行

基点: `artifacts/performance-high-2026-09-09/`。

- `before-cpu/device-report.json`: この実装直前の基準。
- `after-cpu-verified/device-report.json`: 最終実装のPC・スマホCPU切り分け。各実装ファイルSHA-256、入力イベント、CPUプロファイル、5秒窓、スクリーンショット。
- `production-transport.json`: 公開済み旧版の圧縮・ブラウザキャッシュの実測。
- `pc-mcp.json`、`mobile-mcp.json`: DevToolsのトレース要約・分析・ネットワーク／アクセシビリティ。DevTools側が指定フォルダへの直接保存を許可しなかったため、生トレースファイルではなく返された分析結果を保存。
- `after-raw-slow/`、`after-br-slow/`: 低速配信の結果。
- `regression-final/`、`statistics-regression-fixed/`、`legend-regression-fixed/`、`poi-edge-regression/`、`demand-providers/`: 合格した回帰テストと画像。
